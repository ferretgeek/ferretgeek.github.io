CPA-XCPA-XAI 接口服务管理AI service management

github.com/ferretgeek/cliproxyapi-dashboard

为自行部署的 CLIProxyAPI 提供网页管理：服务状态、请求日志与历史用量一目了然；在 Linux / systemd 下可完成带校验与回滚的升级。A web console for self-hosted CLIProxyAPI: service status, request logs, and usage history at a glance, plus verified, rollback-safe upgrades on Linux / systemd.

设计考虑Why进程启动不等于服务可用。把“更新成功”建立在接口验证上，并为失败准备恢复路径。A running process is not necessarily a working service. Verify the real endpoint before reporting success, and keep a way back when it fails.

  • 升级经 SHA-256 校验与原子替换，失败自动回滚SHA-256 checks and atomic replacement, with rollback on failure
  • 重启后调用带认证的管理接口，确认服务可用An upgrade succeeds only when the authenticated API answers
  • 日志增量解析，每轮扫描设字节与时间预算Incremental log parsing with per-scan byte and time budgets

02AI 与开发工具AI & Dev Tools

大模型接口测速LLM API Benchmark

github.com/ferretgeek/llm-api-benchmark

用统一口径比较模型接口：锁定场景逐条请求，分别记录首字延迟、输出速度与 Token 用量，并换算估算成本。Compares model APIs on equal terms: fixed scenarios, one request at a time, with time to first text, output speed, token usage, and estimated cost kept apart.

设计考虑Why不把并发吞吐当成单请求速度，也不把估算当成账单，让结果有明确口径、便于复测。Concurrent throughput is not single-request speed, and an estimate is not a bill. Explicit rules make results easy to read and reproduce.

  • 单流逐条测量，不把并发吞吐当成单请求速度Single-stream runs; concurrent throughput is never called speed
  • 预热计入用量，但不进入正式速度样本Warm-ups count toward usage but stay out of speed samples
  • 完整 usage 与中断估算分开记录并标注Complete usage and interrupted estimates are kept apart
  • Python
  • FastAPI

  • Streaming
  • Docker

03邮件与账号Mail & Accounts

Outlook 授权维护Outlook Token Keeper

github.com/ferretgeek/outlook-token-keeper

集中维护已授权的 Outlook 邮箱：定时刷新令牌、只读检查连接，并记录需要人工处理的异常；不读取邮件正文，也不保存密码。Keeps authorized Outlook mailboxes healthy: scheduled token refresh, read-only connection checks, and a clear list of what needs attention. No message bodies, no passwords.

设计考虑Why批量操作不依赖网页一直开着；敏感字段不仅要加密，还要校验它属于哪个账号，防止密文被错位替换。Batch work should not depend on an open browser tab. Encryption should also prove which account a secret belongs to, rejecting ciphertext moved elsewhere.

  • Web 与后台 Worker 分离，批量任务不依赖网页Web app and background Worker run separately
  • 任务进度存入 PostgreSQL，单 Worker 重启续跑Jobs persist in PostgreSQL; a single Worker resumes on restart
  • 凭据以 AES-256-GCM 加密并绑定账号与字段AES-256-GCM credentials bound to their account and field
  • Python
  • FastAPI
  • PostgreSQL
  • SQLAlchemy
  • OAuth 2.0

05影音与网络Media & Network

局域网视频播放器LAN Video Player

github.com/ferretgeek/android-smb-player

手机和平板通过 SMB 直接浏览、播放电脑或 NAS 上的影片，支持字幕、续播与观看记录；无需拷贝，也无需转码服务。Browse and play videos from a PC or NAS over SMB on phones and tablets, with subtitles, resume, and watch history. No copying, no transcoding server.

设计考虑Why将网络读取、播放控制和本地数据管理拆开，应对不同媒体格式与使用环境，而不只是播放一个示例视频。Network access, playback control, and local data are kept apart to cope with varied formats and conditions, not just a sample video.

  • 基于 smbj 访问 SMB 2/3 共享，电脑端无需伴生服务SMB 2/3 access via smbj, with no companion service on the PC
  • Media3 为主内核，无法解码时自动回退 libVLCMedia3 by default, falling back to libVLC when it cannot decode
  • 共享凭据在设备端加密保存，日志输出前脱敏Share credentials encrypted on device; logs redacted before output

工程理念PrinciplesPRINCIPLES工程理念

比起堆叠功能，我更在意功能背后的工程问题：AI 的表现如何客观衡量？后台任务中断后怎样继续？升级失败后如何恢复？敏感数据应该放在哪里？Beyond adding features, I care about the engineering questions behind them: How should AI performance be measured? How can interrupted jobs resume? What happens when an upgrade fails? Where should sensitive data live?

韧

为失败设计Design for failure

健康检查、事务、任务续跑与备份恢复，让异常始终有路可退。Health checks, transactions, resumable jobs, and backups give every failure a way back.

界

边界清晰Clear boundaries

凭据加密、日志脱敏、只读访问与写入确认，数据去向说得清。Encrypted secrets, redacted logs, read-only access, and confirmed writes keep data flows explainable.

证

交付可验证Verifiable delivery

类型检查、回归测试与 CI，配齐部署和恢复说明，结果可复核。Type checks, regression tests, and CI, with deployment and recovery notes anyone can follow.
